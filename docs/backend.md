# Сервис проектирования устойчивой спутниковой группировки

Описание системы: какую задачу решает, что умеет, какие даёт результаты, как развернуть и где проходят границы её применимости.

---

## 1. Задача

Спутниковая группировка на низкой орбите должна обеспечивать связь наземным пунктам в высоких широтах. Спутники непрерывно движутся, поэтому связь то появляется, то пропадает: аппарат уходит за горизонт, межспутниковый канал выходит за предельную дальность, шлюз попадает на техобслуживание, отдельный аппарат выходит из строя.

Вопрос, на который отвечает система: **какая конфигурация группировки обеспечит заданный уровень связи, и что произойдёт, если что-то откажет.**

Целевой показатель, заданный техническим заданием: доступность сквозного маршрута **«наземный пункт → спутники → шлюз» не ниже 90 %** времени для каждого клиентского пункта.

### Как устроена связь

Трафик идёт строго по цепочке:

```
   клиентский пункт  →  спутник  →  [ спутник → спутник … ]  →  шлюз
        (наземный)       (подъём)     (межспутниковые каналы)    (выход в сеть)
```

Принципиальное ограничение: **наземные пункты не ретранслируют трафик друг через друга.** Клиент не может быть промежуточным звеном, шлюз завершает маршрут. Из-за этого недостаточно, чтобы над пунктом просто пролетал спутник — нужна ещё непрерывная цепочка межспутниковых каналов до шлюза.

## 2. Что умеет система

| Возможность | Что даёт заказчику |
|---|---|
| **Загрузка проекта** | Принимает описание группировки: орбита, плоскости, аппараты, наземные пункты, окно расчёта |
| **Расчёт на горизонте** | Прогоняет заданный интервал (обычно сутки) с заданным шагом и считает связь на каждом моменте |
| **Показатели доступности** | По каждому пункту: доля времени со связью, самый длинный перерыв, среднее число пересылок, достигнута ли цель |
| **Снимок сети** | Состояние группировки в выбранный момент: где аппараты, какие каналы работают, каким маршрутом идёт трафик, какие есть запасные пути |
| **Редактирование варианта** | Изменение этапа развёртывания, разворота и фазы орбитальных плоскостей, перечня отказов — без перезагрузки исходных данных |
| **Сравнение вариантов** | Сопоставление двух и более расчётов с обоснованием выбора и перечнем ограничений |
| **Анализ отказа** | «Что если откажет этот аппарат или шлюз»: кто пострадает, насколько, какие уязвимости вскрылись и что с этим делать |
| **Выгрузка результата** | Полный отчёт в машиночитаемом виде; его можно загрузить обратно и продолжить работу |

## 3. Основные понятия

| Термин | Значение |
|---|---|
| **Проект** | Сохранённый вариант конструкции группировки. Хранит исходную версию и текущую (с правками), поэтому правки всегда можно откатить |
| **Прогон** | Результат расчёта проекта на всём временном окне. Привязан к той конфигурации, что была на момент запуска |
| **Горизонт** | Длительность расчётного окна, обычно 86 400 с (сутки). Предел — 172 800 с (двое суток) |
| **Шаг сетки** | Интервал между расчётными моментами, обычно 120 с. Сутки с шагом 120 с — это 720 расчётных моментов |
| **Этап развёртывания** | Какие очереди запуска уже на орбите: 1, 2 или 3. Аппарат активен, если его очередь не превышает текущий этап |
| **Клиентский пункт** | Наземный терминал, которому нужна связь |
| **Шлюз** | Наземная станция выхода в сеть, конечная точка маршрута |
| **Межспутниковый канал (ISL)** | Связь между двумя аппаратами. Работает, если расстояние меньше предельного и линия не перекрыта Землёй |
| **Угол места** | Высота аппарата над горизонтом с точки зрения наземного пункта. Ниже порога (обычно 10°) связь не устанавливается |

---

## 4. Что подаётся на вход

Проект описывается одним файлом. Состав:

**Параметры орбиты и расчёта**
- высота орбиты (допустимо 200–1200 км) и наклонение;
- горизонт и шаг расчёта;
- минимальный угол места для связи с землёй;
- предельная дальность межспутникового канала;
- целевая доступность (0.9 = 90 %).

**Конструкция группировки**
- этап развёртывания (1–3);
- орбитальные плоскости: разворот и фаза;
- аппараты: принадлежность плоскости, положение в ней, очередь запуска.

**Наземный сегмент**
- клиентские пункты и шлюзы с координатами.

**Нештатные события**
- отказы аппаратов: какой аппарат и на каком интервале не работает;
- недоступность шлюзов: какой шлюз и когда выключен.

Входные данные проверяются дважды — собственным контролем сервиса и эталонным расчётным модулем организаторов. Некорректный проект отклоняется с указанием конкретного поля, а не общим «ошибка данных». Например: `planes[2].raan_deg must be in [0, 360)`.

## 5. Что получается на выходе

### Показатели по каждому пункту

| Показатель | Смысл |
|---|---|
| **Доступность маршрута** | Доля расчётных моментов, когда сквозной путь до шлюза существует. Это и есть основной критерий ТЗ |
| **Доступность видимости** | Доля моментов, когда над пунктом есть хотя бы один работающий аппарат выше порога угла места |
| **Максимальный перерыв** | Самый длинный непрерывный интервал без связи, в секундах |
| **Среднее число пересылок** | Сколько звеньев в среднем проходит трафик. Считается только по моментам со связью |
| **Цель достигнута** | Да/нет: доступность маршрута не ниже заданного порога |
| **Перечень перерывов** | Каждый разрыв отдельно: начало, конец, длительность и причина |

Разделение двух видов доступности — не формальность, а диагностика. Если видимость высокая, а доступность маршрута низкая, значит, аппараты над пунктом есть, но межспутниковая сеть до шлюза разорвана. Лечится это не добавлением аппаратов над пунктом, а дальностью каналов или геометрией плоскостей.

### Причины перерывов

Каждый разрыв связи получает объяснение, а не просто отметку «связи нет»:

| Причина | Что произошло | Куда смотреть |
|---|---|---|
| **Нет видимого аппарата** | Над пунктом нет спутника выше порога угла места | Число аппаратов, фазировка плоскостей |
| **Нет контакта со шлюзом** | Аппараты есть, но ни один не видит шлюз | Расположение шлюзов, их количество |
| **Разрыв межспутниковой сети** | Оба конца в порядке, но цепочки между ними нет | Предельная дальность канала, развороты плоскостей |
| **Шлюз недоступен** | Наземный выход выключен | Резервирование шлюзов |

### Снимок сети на выбранный момент

Для любого момента внутри горизонта система показывает: положение всех аппаратов, какие каналы активны, какие аппараты видит выбранный пункт, каким маршрутом идёт трафик и какие есть запасные пути.

Дополнительно выдаётся **объяснение изменения** относительно предыдущего момента. Различаются два случая, внешне выглядящих одинаково: прежний путь ещё работоспособен, но найден другой равноценный по длине; либо прежний путь распался — аппарат ушёл за горизонт или канал вышел за дальность.

### Выбор маршрута

Маршрут ищется по критерию **минимального числа пересылок**, а не минимального расстояния: каждая пересылка — это отдельный радиоканал и дополнительная задержка.

Вместе с маршрутом выдаётся его обоснование: название метода, критерий оптимизации, перечень ограничений и объяснение, почему выбран именно такой критерий. Также выдаются запасные пути — равные по длине и на одну пересылку длиннее. Они показывают, есть ли у направления обходной вариант при отказе узла.

Расчёт **детерминирован**: одинаковый вход всегда даёт побайтово одинаковый результат. Повторный запрос не покажет другой маршрут из числа равноценных.

### Выгрузка

Полный отчёт по прогону: итоговая конфигурация, все маршруты по всем моментам, показатели и краткое заключение. Отчёт можно загрузить обратно в систему как новый проект и продолжить работу с той конфигурации, на которой остановились.

## 6. Сравнение вариантов

Сопоставляются два и более прогона. Варианты ранжируются последовательно:

1. сколько пунктов достигли цели;
2. средняя доступность маршрута;
3. средний максимальный перерыв.

При полном совпадении фиксируется ничья — система не изобретает победителя там, где расчёт его не даёт.

Для двух вариантов дополнительно показывается, **чем именно** отличаются конфигурации: этап развёртывания, параметры орбиты, развороты плоскостей, перечни отказов.

### Обоснование, а не просто вердикт

Система обязана объяснять свой выбор, поэтому к рекомендации прилагаются четыре блока:

- **Преимущества** — чем именно выбранный вариант лучше, с числами;
- **Условия** — при каких допущениях получен вывод: какая цель, какие пункты, какой этап, какая дальность каналов, учитывались ли отказы;
- **Ограничения** — чего расчёт **не** проверял;
- **Заключение** — итоговая формулировка.

Блок ограничений намеренно самокритичен и подсказывает следующий шаг. Примеры формулировок, которые система выдаёт сама:

> Один шлюз G_MUR — единая точка выхода; отказ шлюза этим сравнением не проверялся.

> Расчёт только на горизонте 86 400 с; за пределами окна доступность не проверялась.

> Неполная группировка (этап 2 из 3): аппараты более поздних очередей неактивны, запас по отказам ограничен.

Смысл в том, чтобы рекомендация не выглядела более уверенной, чем позволяют исходные данные.

## 7. Анализ устойчивости к отказам

Проверка «что если откажет вот этот узел». Отказавший аппарат либо указывается прямо, либо определяется автоматически — берётся аппарат с текущего маршрута выбранного пункта. Можно вывести из строя и шлюз. Интервал отказа задаётся или по умолчанию длится до конца горизонта.

Система пересчитывает весь горизонт с учётом отказа и выдаёт:

- **кто пострадал, а кто нет** — поимённый перечень затронутых и сохранивших связь пунктов;
- **маршрут до и после** по каждому пункту;
- **насколько просели показатели** — изменение доступности и максимального перерыва;
- **сколько моментов связи потеряно** внутри интервала отказа;
- **уязвимости** — в частности, если один аппарат оказался общей точкой отказа сразу для нескольких пунктов, это указывается явно;
- **меры** — конкретные рекомендации, подобранные по фактическим причинам разрывов: увеличить дальность межспутникового канала, сместить развороты плоскостей, добавить резервный шлюз, поднять этап развёртывания.

Исходный расчёт при этом не портится — анализ отказа выполняется на отдельной копии.

Отдельно оговаривается методическая тонкость: вариант с искусственно внесённым отказом **не является альтернативной конструкцией**. Это тот же проект со сломанным узлом, и сравнение с ним отвечает на вопрос «выдержит ли», а не «что лучше построить». Система формулирует это прямо в результате, чтобы вывод не был прочитан неверно.

## 8. Типовой порядок работы

1. **Загрузить проект.** Полная группировка, сутки расчёта.
2. **Запустить расчёт.** Получить показатели по всем пунктам и сразу увидеть, кто достигает цели.
3. **Разобрать проблемный момент.** Открыть снимок сети на интересующем времени: маршрут, запасные пути, причина перерыва.
4. **Сравнить с первой очередью.** Понизить этап развёртывания, пересчитать, сопоставить с полной группировкой и получить обоснование выбора.
5. **Проверить отказ.** Вывести из строя аппарат с действующего маршрута и посмотреть, кто теряет связь и какие меры предлагаются.
6. **Выгрузить результат.** Отчёт пригоден и для сдачи, и для повторной загрузки в систему.
7. **Откатить правки.** Сброс возвращает проект к исходной версии; при необходимости вариант можно скопировать и вести две ветки проработки параллельно.

### Контрольные наборы данных

В комплекте четыре сценария, каждый демонстрирует свой режим работы:

| Набор | Средняя доступность маршрута | Что показывает |
|---|---|---|
| Полная группировка | ~98 % | Штатный режим: все пункты достигают цели 90 % |
| Первая очередь | ~19 % | Неразвёрнутая группировка: цель недостижима ни для кого |
| Отказы аппаратов | ~81 % | Отказы опускают показатели ниже цели |
| Ограниченная дальность канала | ~68 % при видимости 98–100 % | Аппараты видны, но межспутниковая сеть распалась |

Последний набор особенно показателен: он демонстрирует, что одной видимости спутников недостаточно для связи.

## 9. Развёртывание

### Вариант 1: Docker (рекомендуемый)

Единственное требование к машине — установленный Docker. Всё остальное (среда исполнения, расчётный модуль, библиотеки) собирается внутри образа.

```bash
docker compose up --build
```

Сервис поднимается на `http://localhost:8080`. Остановка — `Ctrl+C`, затем `docker compose down`.

Без Compose:

```bash
docker build -t kosmohak-nn .
docker run --rm -p 8080:8080 kosmohak-nn
```

Образ собирается в два этапа: сначала компилируется сервис, затем итоговый образ комплектуется расчётным модулем и его зависимостями. Процесс работает от непривилегированного пользователя. Встроена автоматическая проверка работоспособности — Docker сам отслеживает состояние контейнера.

### Вариант 2: запуск из исходников

Требуется Go 1.23+ и Python 3.10+ с библиотекой NumPy.

```bash
python3 -m pip install numpy
make tidy
make run
```

### Настройки

Задаются переменными окружения, все имеют рабочие значения по умолчанию:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес и порт |
| `PYTHON_BIN` | `python3` | Интерпретатор расчётного модуля |
| `RUNNER_SCRIPT` | `python/runner.py` | Путь к расчётному модулю |
| `CORS_ORIGINS` | `*` | Разрешённые источники запросов из браузера |

Чтобы занять другой внешний порт, меняется публикация порта в `docker-compose.yml` — например, `"3000:8080"` откроет сервис на `http://localhost:3000`.

### Проверка после установки

```bash
curl http://localhost:8080/health
# {"status":"ok"}
```

Далее — загрузить контрольный набор и убедиться, что расчёт проходит:

```bash
curl -s -X POST http://localhost:8080/api/projects \
  -H 'Content-Type: application/json' \
  --data-binary @data/01_full_constellation.json
```

Ответ с кодом 201 и идентификатором проекта означает, что и сервис, и расчётный модуль работают.

### Эксплуатационные замечания

- **Данные хранятся в памяти процесса.** Перезапуск контейнера очищает все проекты и прогоны. Внешняя база данных не требуется и не используется. Результаты, которые нужно сохранить, следует выгружать.
- **Авторизации нет**, доступ открыт всем, кто видит порт. Сервис рассчитан на демонстрационный контур, а не на публикацию в открытую сеть.
- **Масштабирование горизонтальное не предусмотрено:** экземпляры не разделяют состояние, запрос должен попадать в тот же экземпляр, где создавался проект.

## 10. Производительность

Замеры на контрольном наборе «полная группировка» — 48 аппаратов, 3 плоскости, 3 клиентских пункта, 1 шлюз, сутки расчёта с шагом 120 с (720 расчётных моментов):

| Операция | Время |
|---|---|
| Загрузка и проверка проекта | ~0.2 с |
| **Полный расчёт суток** | **~0.65 с** |
| Снимок сети на момент | ~0.17 с |
| Анализ отказа (включая повторный расчёт суток и сравнение) | ~1.0 с |
| Выгрузка отчёта (~167 КБ) | мгновенно |

Все операции синхронные: ответ приходит по готовности, фоновых задач и опроса статуса нет. Предельное время обработки запроса — 5 минут, что даёт примерно 450-кратный запас к текущему времени расчёта.

Масштабирование нагрузки: время расчёта растёт пропорционально числу расчётных моментов и числу клиентских пунктов. Удвоение горизонта или уменьшение шага вдвое примерно удваивает время.

## 11. Границы применимости

Что следует учитывать при интерпретации результатов:

- **Расчёт ведётся в пределах заданного окна.** Что происходит за его границами, не проверяется. Перерыв, упирающийся в конец горизонта, не «переносится» на начало.
- **Геометрия орбит идеализирована.** Используется эталонный расчётный модуль организаторов, в него не вносилось изменений. Возмущения орбит, погодные условия, помехи и энергобаланс аппаратов не моделируются.
- **Связь бинарна.** Канал либо есть, либо нет. Пропускная способность, качество сигнала и объём трафика не учитываются.
- **Наземные пункты не ретранслируют трафик** — это заданное условие задачи, а не ограничение реализации.
- **Отказы задаются вручную.** Система считает последствия заданного отказа, но не оценивает вероятность его наступления и не перебирает все возможные комбинации отказов автоматически.
- **Диапазоны параметров ограничены:** высота орбиты 200–1200 км, горизонт до 48 часов, дальность межспутникового канала до 10 000 км. Значения вне диапазонов отклоняются на входе.

## 12. Соответствие техническому заданию

| Требование ТЗ | Как выполнено |
|---|---|
| Доступность сквозного пути ≥ 90 % для каждого пункта | Считается по каждому пункту отдельно, порог настраивается, результат «достигнута / не достигнута» выдаётся явно |
| Наземные пункты не ретранслируют трафик | Заложено в модель маршрутизации: клиент не может быть транзитом, шлюз завершает маршрут |
| Использование эталонного расчётного модуля без правок | Модуль подключён как есть; корректность стыковки проверяется автоматическими тестами на всех четырёх контрольных наборах |
| Объяснимость решений | Каждый маршрут сопровождается обоснованием критерия; каждый перерыв — причиной; каждая рекомендация — преимуществами, условиями и ограничениями |
| Анализ устойчивости к отказам | Отказ аппарата или шлюза с разбором последствий, выявлением общих точек отказа и перечнем мер |
| Сравнение вариантов конструкции | Сравнение двух и более расчётов с ранжированием и обоснованием выбора |
| Выгрузка результата | Полный машиночитаемый отчёт, пригодный для обратной загрузки |

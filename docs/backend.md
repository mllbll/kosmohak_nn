## 1. Что делает сервис

Считает устойчивость спутниковой группировки к отказам. Пользователь загружает сценарий (`cosmo-A-1.0`): орбитальная конфигурация, наземные пункты, окно расчёта. Сервис прогоняет временную сетку, на каждом шаге строит граф связности, ищет маршрут `клиент → спутники → шлюз` и сводит результат в метрики доступности.

Ключевое ограничение предметной области, которое пронизывает весь код: **наземные пункты не ретранслируют трафик**. Путь всегда `client → sat [→ sat …] → gateway`, клиент не может быть транзитом, шлюз — терминал маршрута.

Целевой показатель ТЗ — доля шагов сетки с найденным маршрутом (`path_ratio`) ≥ `target_availability` (обычно 0.9) для каждого клиентского пункта.

### Границы

Сервис **не** делает: авторизацию, персистентность, очереди, фоновые задачи, многопроцессность. Один процесс, память процесса, синхронные обработчики. Перезапуск = потеря всех проектов и прогонов.

## 2. Запуск для разработки

```bash
python3 -m pip install numpy     # обязателен: geometry.py на NumPy
make tidy
make run                         # :8080
make test                        # go test ./...
```

Go 1.23+, Python 3.10+. Проверить, что Python-часть жива, без поднятия сервиса:

```bash
python3 python/runner.py data/01_full_constellation.json 0   # один снимок
python3 python/runner.py data/01_full_constellation.json     # весь горизонт, NDJSON
```

Если `python3` не в `PATH` или нет NumPy, Go соберётся и запустится, но **любой** эндпоинт, трогающий геометрию, вернёт 422. Это самая частая причина «всё сломалось» на новой машине.

## 3. Архитектура

Три слоя плюс клиент к внешнему счётчику. Зависимости идут строго вниз, через интерфейсы:

```
                      cmd/main.go
                           │  config.Load(), signal.NotifyContext
                           ▼
                    internal/app
                    ├── app.go   chi-роутер, middleware, маршруты
                    └── di.go    ленивый DI-контейнер
                           │
       ┌───────────────────┼───────────────────┐
       ▼                   ▼                   ▼
  api/project/v1      api/run/v1         api/response.go
  (HTTP → model)      (HTTP → model)     (JSON + error→status)
       │                   │
       ▼                   ▼
  service.ProjectService   service.RunService          ← интерфейсы в service/service.go
  service/project/…        service/run/…               ← реализации
       │                   │         │
       ▼                   ▼         ▼
  repository.ProjectRepository  RunRepository     client/geometry.Client
  repository/project/…          repository/run/…  client/geometry/…
       (in-memory + RWMutex)                            │
                                                        ▼
                                              python/runner.py → geometry.py
```

Правила, которых придерживается код:

- **Один хендлер — один файл.** `api/run/v1/create.go`, `…/export.go` и т. д. То же в сервисах и репозиториях.
- **Интерфейс объявлен у потребителя, реализация — в подпакете.** `service/service.go` описывает `RunService`, реализация в `service/run`. Так же для репозиториев (`repository/repository.go`) и геометрии (`client/geometry/interface.go`).
- **Слои общаются доменными типами** из `internal/model`. HTTP-слой не знает о репозиториях, репозиторий не знает о HTTP.
- **DI ленивый и без магии** — [internal/app/di.go](../internal/app/di.go). Каждый геттер создаёт зависимость при первом обращении и кэширует. Нет кодогенерации, нет рефлексии; чтобы подменить реализацию, правится один геттер.

### Путь запроса

На примере `POST /api/projects/{id}/runs`:

1. `app.go` → `runAPI.Create` — достаёт `id` из URL (`chi.URLParam`), собирает `model.CreateRunRequest`.
2. `service/run/create.go` → `Create` — читает проект из репозитория, вызывает `execute`.
3. `execute` — один запуск Python на весь горизонт, на каждом снимке считает маршруты всех клиентов, затем агрегирует метрики.
4. Прогон кладётся в `RunRepository`, наружу отдаётся сокращённый ответ (`run_id` + метрики), 201.
5. Ошибка любого слоя всплывает как `error` и превращается в статус в `api.WriteError`.

## 5. Конфигурация

Всё через ENV, читается один раз при старте ([config.go](../internal/config/config.go)):

| Переменная | Дефолт | Назначение |
|---|---|---|
| `HTTP_ADDR` | `:8080` | Адрес прослушивания |
| `PYTHON_BIN` | `python3` | Интерпретатор для `runner.py` |
| `RUNNER_SCRIPT` | `python/runner.py` | Путь к скрипту; **относительный путь резолвится от рабочего каталога процесса** |
| `CORS_ORIGINS` | `*` | Список origin через запятую; пустое значение схлопывается в `*` |

Конфига-файла нет и не нужно. Пустая строка в ENV трактуется как «не задано» — `getenv` возвращает дефолт.

Таймауты заданы в коде, не в ENV: `ReadHeaderTimeout` 10 с, `middleware.Timeout` 5 минут на запрос. Пятиминутный лимит существует ради `POST /runs` и `what-if`, которые синхронно ждут Python.

## 6. Доменная модель

### Scenario — вход расчёта

[internal/model/scenario.go](../internal/model/scenario.go). Ровно та структура, что лежит в `data/*.json`, тег в тег. Схема `cosmo-A-1.0`.

```
Scenario
├── Environment   altitude_km, inclination_deg, earth_angle0_deg,
│                 horizon_s, step_s, min_elevation_deg,
│                 isl_range_km, target_availability
├── Design        launch_stage, []Plane{id, raan_deg, phase_deg},
│                 []Satellite{id, plane_id, slot_deg, launch_batch}
├── GroundSites   []{id, name, role: client|gateway, lat_deg, lon_deg}
├── Failures      []{satellite_id, start_s, end_s}
└── GatewayOutages []{gateway_id, start_s, end_s}
```

Полезные методы на `Scenario`:

- `TimeGrid()` — `[0, step, 2·step, …)`, **правый конец горизонта не входит**. При `horizon_s=86400, step_s=120` это 720 шагов, последний `86280`. Эта деталь определяет знаменатель всех метрик.
- `ClientIDs()` / `GatewayIDs()` — фильтр по `role`, порядок сохраняется из исходного JSON. Порядок клиентов = порядок метрик в ответах.
- `IsGatewayOutaged(id, t)` — полуинтервал `[start_s, end_s)`.
- `CloneScenario` — глубокая копия всех слайсов. Вызывается везде, где сценарий пересекает границу слоя, чтобы мутация одного объекта не протекла в другой. Если добавляете в `Scenario` новый слайс — **добавьте его в `CloneScenario`**, иначе получите общий backing array между проектом и прогоном.

### Project — сохранённый вариант

```go
type Project struct {
    ID        string
    Base      Scenario  // как загрузили, не меняется
    Effective Scenario  // с применёнными PATCH
}
```

`Base` нужен ради `POST /reset`: сброс — это `Effective = CloneScenario(Base)`. `PATCH` меняет только `Effective`. Прогон всегда считается по `Effective`.

### Run — результат расчёта

```go
type Run struct {
    ID, ProjectID     string
    EffectiveScenario Scenario        // снимок конфига на момент расчёта
    Routes            []RouteRecord   // len == len(grid) × len(clients)
    Metrics           []ClientMetrics
    Summary           string
}
```

`EffectiveScenario` копируется в прогон намеренно: последующий `PATCH` проекта не должен задним числом менять смысл уже посчитанного прогона. На этой копии работают `snapshot`, `export`, `compare` и `what-if`.

`RouteRecord.AltCount` сериализуется всегда, включая `0` — у поля нет `omitempty`. Непустой `path` при `alt_count: 0` означает «маршрут ровно один», и UI отличает это от «поле не пришло». Сами альтернативные пути в прогоне не хранятся (на 720 шагах это заметный объём) — их отдаёт только `GET /snapshot`.

### Snapshot — выход Python

[internal/model/snapshot.go](../internal/model/snapshot.go). Единственное место с ручным JSON-кодеком: `Edge` в Python — массив `["id_1", "id_2", 1234.5]`, в Go — структура. `UnmarshalJSON`/`MarshalJSON` на `Edge` переводят одно в другое и валидируют длину и типы. Рёбра двунаправленные и не размечены по типу — деление на «клиент–спутник», «ISL» и «спутник–шлюз» делает уже Go, по ролям узлов.

## 7. Мост Go ↔ Python

`python/geometry.py` — эталон организаторов, **править нельзя**. Всё взаимодействие с ним изолировано в `internal/client/geometry` за интерфейсом:

```go
type Client interface {
    Snapshot(ctx, sc Scenario, t float64) (Snapshot, error)
    WalkSnapshots(ctx, sc Scenario, fn func(Snapshot) error) error
}
```

### Механика вызова

Обе операции устроены одинаково ([snapshot.go](../internal/client/geometry/snapshot.go), [walk.go](../internal/client/geometry/walk.go)):

1. `writeTempScenario` сериализует сценарий во временный файл (`os.CreateTemp`, `SetEscapeHTML(false)`), `defer cleanup()` удаляет его.
2. `exec.CommandContext(ctx, PYTHON_BIN, RUNNER_SCRIPT, path[, t])` — контекст запроса прокинут в процесс, отмена запроса убивает Python.
3. `cmd.Output()` — stdout в память, stderr в `ExitError.Stderr`.
4. Разбор: `Snapshot` — один JSON-объект; `WalkSnapshots` — `json.Decoder` в цикле по NDJSON (`runner.py` печатает по строке на шаг), каждый снимок отдаётся в колбэк.

Стоимость: **один процесс Python на вызов**. `POST /runs` — один процесс на весь горизонт (дёшево). `GET /snapshot` — один процесс на каждый запрос (дороже относительно, но это ~0.17 с). Кэша снимков нет.

Почему файл, а не stdin: `runner.py` принимает путь, потому что `geometry.load()` читает файл — а его сигнатуру мы не меняем.

### Классификация ошибок Python

[error.go](../internal/client/geometry/error.go) разбирает stderr и решает, чья это вина:

- stderr содержит `ValueError:`, `JSONDecodeError:`, `TypeError:`, `KeyError:` → ошибка входных данных → `ErrInvalidArgument` → **400**;
- всё остальное (нет интерпретатора, нет NumPy, MemoryError, сегфолт) → `ErrGeometryFailed` → **422**.

`extractPythonError` идёт по трейсбеку снизу вверх и вытаскивает текст последнего распознанного исключения — в ответ уходит `Invalid orbit`, а не двадцать строк стека.

### Двойная валидация — это не дублирование

Go-валидатор [validate.go](../internal/service/project/validate.go) повторяет правила `geometry.validate()`. Так сделано намеренно:

- Go даёт **адресные** сообщения (`planes[2].raan_deg must be in [0, 360)`) вместо питоновского `Invalid plane angle`;
- отсекает мусор до запуска процесса;
- но Python остаётся источником истины — поэтому `Create`, `Patch` и `WhatIf` после своей валидации **дополнительно** дёргают `Snapshot(ctx, sc, 0)` как smoke-тест. Если эталон отверг сценарий, проект не создастся.

При правке правил валидации сверяйтесь с `geometry.validate()` — расхождение означает либо принятый сценарий, падающий на первом же прогоне, либо отклонённый валидный.

## 8. Ядро: как считается маршрут

Весь алгоритм в [internal/service/run/route.go](../internal/service/run/route.go). Функция `Route(sc, snap, clientID) RouteResult` — чистая, без I/O; её можно дёргать из тестов напрямую.

### Граф

`buildRouteGraph` строит списки смежности из рёбер снимка и размечает узлы по ролям: `sats` (только `active == true`), `gateways`, `clients`, `outagedGW` (шлюзы, у которых сейчас outage). Списки смежности сортируются `sort.Strings` — **это и есть источник детерминизма**: при равных по длине маршрутах BFS/DFS всегда выберет лексикографически первый, и ответ на одинаковый вход побайтово одинаков. Не убирайте сортировку.

### Допустимость перехода

`allowedHop(from, to)` кодирует предметное ограничение:

| Из | В спутник | В шлюз | В клиента |
|---|---|---|---|
| Клиент | ✅ | ❌ | ❌ |
| Спутник | ✅ | ✅ (если не в outage) | ❌ |
| Шлюз | ❌ | ❌ | ❌ |

Шлюз не имеет исходящих переходов — маршрут на нём останавливается. Клиент недостижим как цель — наземные пункты не транзит.

### Поиск

1. `shortestHops` — BFS от клиента, возвращает дистанцию до **первого встреченного** шлюза (`minHops`) или `-1`.
2. `enumerateAtHops(client, g, minHops, 4)` — DFS с отсечением по глубине, собирает до 4 путей ровно такой длины.
3. `enumerateAtHops(client, g, minHops+1, 2)` — до 2 «запасных» путей на один hop длиннее.
4. `Path` = первый из min-hop путей, `Alternatives` = остальные min-hop + запасные.

Критерий — число hops, а не километры: каждый hop это отдельный радиоканал и задержка. Обоснование выбора уезжает в ответ в `route.algorithm` (`name`, `objective`, `constraints`, `rationale`) — это требование ТЗ «объяснимость», а не отладочное поле.

Лимиты `maxMinHopPaths = 4` и `maxBackupPaths = 2` — константы в начале файла. Подъём лимита квадратично бьёт по времени `GET /snapshot` на плотном графе (в снимке полной группировки ~86 рёбер).

### Причины разрыва

Когда маршрута нет, `classifyGap` ставит одну из четырёх причин, **в этом порядке приоритета**:

| Причина | Условие | Смысл для пользователя |
|---|---|---|
| `gateway_outage` | все шлюзы в outage на момент `t` | Наземный сегмент выключен |
| `no_visible_sat` | у клиента нет ни одного допустимого перехода | Над пунктом нет спутника выше `min_elevation_deg` |
| `no_gateway_contact` | ни один шлюз не видит спутник | Спутник есть, но «приземлиться» негде |
| `isl_partition` | оба конца в порядке, пути нет | Межспутниковая сеть разорвана: `isl_range_km` мал или дыра в плоскостях |

Порядок важен: при одновременном совпадении условий пользователь должен увидеть корневую причину, а не первую попавшуюся.

### Дельта сети

`networkDelta` сравнивает текущий маршрут с маршрутом предыдущего шага сетки и отвечает на вопрос «почему путь изменился». `pathStillValid` перепроверяет старый путь на текущем графе — так различаются два случая, которые снаружи выглядят одинаково:

- **старый путь ещё валиден**, но BFS выбрал другой min-hop (детерминированный, но иной выбор);
- **старый путь распался** — узел ушёл за горизонт или ребро вышло за `isl_range_km`.

Объяснение уходит в `network_delta.explanation` текстом.

## 9. Метрики

[internal/service/run/metrics.go](../internal/service/run/metrics.go), функция `Aggregate`. Знаменатель везде — число шагов сетки `n = len(TimeGrid())`.

| Метрика | Как считается |
|---|---|
| `visibility_ratio` | доля шагов, где клиент видит хотя бы один активный спутник выше `min_elevation_deg` |
| `path_ratio` | доля шагов с непустым маршрутом — **основной показатель ТЗ** |
| `max_gap_s` | самая длинная серия подряд идущих шагов без маршрута × `step_s` |
| `mean_hops` | среднее число hops **по шагам с маршрутом** (шаги без маршрута не занижают среднее) |
| `meets_target` | `path_ratio >= target_availability` |
| `gaps[]` | интервалы `[start_s, end_s)` с доминирующей причиной внутри каждого |

Две неочевидности, которые ломают сравнение с наивной реализацией:

**Разрывы не склеиваются через границы окна.** Разрыв, начавшийся до `t=0`, и разрыв, упирающийся в конец горизонта, — два отдельных интервала. Кольцевой склейки «через полночь» нет: расчёт идёт на конечном окне, а не на периодической орбите.

**`visibility_ratio` и `path_ratio` считаются по-разному.** Видимость берётся из `snapshot.elevation_deg` — карты, которую Python отдаёт для **всех** наземных пунктов и **только активных** спутников, без фильтра по `min_elevation_deg` (фильтрует уже Go в `clientVisible`). Маршрут же учитывает ещё и ISL-связность и состояние шлюза. Отсюда типичная картина фикстуры `04_link_range`: видимость ~98–100 %, а `path_ratio` ~0.68 — спутники над головой есть, но сеть между ними распалась.

Важный нюанс для отладки: у шлюза в outage Python всё равно выдаёт его `elevation_deg`, но **не выдаёт рёбер**. Видимость и связность — разные вещи.

`gaps[].reason` — не первая и не последняя причина в интервале, а **самая частая** (`dominantReasonCount`). Для длинного разрыва со сменой причин показывается преобладающая.

## 10. Compare и обоснование выбора

[compare.go](../internal/service/run/compare.go) + [justification.go](../internal/service/run/justification.go).

Вход — два прогона (`run_a`/`run_b`) или N ≥ 2 (`run_ids`). Первым делом `sameTimeGrid` требует совпадения `horizon_s` и `step_s`: сравнивать доли, посчитанные на разных знаменателях, бессмысленно → 400.

Ранжирование вариантов, лексикографически (`cmpVariant`):

1. больше клиентов, достигших цели;
2. выше средний `path_ratio`;
3. ниже средний `max_gap_s`.

Полное совпадение по всем трём → `tie`. Для клиентов свой компаратор (`cmpClientMetric`): `meets_target` → `path_ratio` → `max_gap_s`.

При ровно двух прогонах дополнительно считается `config_diff` — что именно различается в конфигурации (`launch_stage`, поля `environment`, `raan/phase` плоскостей, списки отказов), и `better` схлопывается в `"a"`/`"b"`/`"tie"`. При N > 2 этих полей нет, работают `variants[]` и `clients[].by_run[]`.

`justification.go` собирает человекочитаемое обоснование — `advantages`, `conditions`, `limitations`, `conclusion`. Это прямое требование ТЗ: система обязана не просто выбрать вариант, а объяснить при каких условиях он лучше и чего расчёт **не** проверял. `limitationsOf` намеренно самокритичен и сам подсказывает следующий шаг: «один шлюз — единая точка выхода, нужен what-if с `gateway_id`», «за пределами горизонта доступность не проверялась».

Текст собирается через `uniqueAppender` — замыкание с дедупликацией, чтобы при N вариантах один и тот же довод не повторился N раз.

## 11. What-if и анализ устойчивости

[what_if.go](../internal/service/run/what_if.go), [resilience.go](../internal/service/run/resilience.go).

Запрос — «что если откажет вот этот узел». Цель отказа определяется в `resolveFailure` по убыванию явности:

1. явный `satellite_id` и/или `gateway_id` из тела (проверяются на существование);
2. иначе — спутник **с маршрута** клиента `client_id` в момент `t_s` (`satelliteFromPath` берёт первый спутник пути). Это сценарий «ткнули в узел на карте».

Интервал отказа: `start_s` (по умолчанию `t_s`) … `end_s` (по умолчанию до конца горизонта).

Важный побочный эффект, о котором надо знать: **what-if создаёт новый проект и новый прогон**. Не мутирует исходные. У нового проекта `Base` = исходный `Effective`, а `Effective` = он же плюс дописанный `Failure`/`GatewayOutage`. Дальше — обычный `execute`, затем `Compare(original, new)`.

`annotateWhatIfCompare` затем **переписывает вердикт сравнения**. Без этого получалась смысловая ошибка: compare честно сообщал, что «run_b хуже», а UI показывал это как «рекомендуем вариант A» — хотя run_b вообще не конкурирующая конструкция, а тот же дизайн со сломанным узлом. Поэтому `better` принудительно ставится в `"a"`, а в `limitations` первой строкой уходит оговорка «run_b — прогон с искусственным отказом, а не альтернативная конструкция группировки».

`buildResilienceAnalysis` даёт разбор по клиентам: путь до и после, дельты метрик, сколько шагов внутри окна отказа потеряно (`windowStats`), доминирующая причина разрыва. Клиент считается затронутым, если потерял шаги, просел по `path_ratio`, вырос `max_gap_s` или маршрут исчез совсем.

Отдельно детектируется **общая точка отказа**: если один спутник лежал на маршрутах нескольких клиентов, это попадает в `vulnerabilities` явной строкой. `mitigations` предлагает контрмеры, выбирая их по фактическим причинам разрывов (разрыв ISL → поднять `isl_range_km` или сдвинуть RAAN; отказ шлюза → дублировать шлюз; и т. д.).

## 12. Хранилище

`map[string]T` под `sync.RWMutex`, отдельно для проектов и прогонов. Ни удаления, ни списка, ни TTL, ни вытеснения — **память растёт монотонно**. На хакатонной нагрузке это осознанный размен, но знать стоит: каждый what-if добавляет проект и прогон, а прогон на сутки содержит 720 × N клиентов записей маршрутов (экспорт такого прогона — ~167 КБ JSON).

Между доменной моделью и хранилищем есть слой `repository/model` + `repository/converter`. Сейчас репо-модели структурно совпадают с доменными, и слой выглядит избыточным — он оставлен как шов: при переезде на Postgres меняются конвертеры, а сервисы не трогаются.

Конвертеры **везде делают глубокие копии** (`CloneScenario`, `cloneRoutes`, `cloneMetrics`) на входе и на выходе. Без этого вызывающий код получил бы ссылку на слайс внутри хранилища и смог бы испортить его на месте. Если добавляете поле-слайс в `Run` или `Project` — продублируйте копирование в конвертере.

## 13. Ошибки и HTTP-статусы

Четыре сентинела в [internal/model/errors.go](../internal/model/errors.go), оборачиваются через `fmt.Errorf("%w: …")` и разматываются в одном месте — [api/response.go](../internal/api/response.go):

| Сентинел | Статус | Когда |
|---|---|---|
| `ErrInvalidArgument` | 400 | битый JSON, провал валидации, неизвестный клиент/спутник/плоскость, `t_s` вне `[0, horizon_s]`, разные сетки в compare, `ValueError` из Python |
| `ErrProjectNotFound`, `ErrRunNotFound` | 404 | неизвестный UUID |
| `ErrGeometryFailed` | 422 | Python не запустился, упал не по валидации, вернул не то число снимков |
| (всё прочее) | 500 | непредусмотренное |

Тело ошибки всегда `{"error": "текст"}`. Проверено на живом сервисе:

```
HTTP 400  битый schema_version
HTTP 404  GET /api/runs/does-not-exist
HTTP 400  snapshot?t_s=999999        (за горизонтом)
HTTP 400  snapshot?client_id=NOPE
HTTP 400  compare только с одним run id
```

Добавляете новый класс ошибок — заводите сентинел в `model` и ветку в `WriteError`. Не пишите статусы в хендлерах: тогда маппинг перестанет быть единым.

### Защита от рассинхрона с Python

`execute` проверяет поток снимков построчно и падает с `ErrGeometryFailed`, если:

- снимков пришло больше, чем шагов в сетке;
- `snap.t_s` не совпал с ожидаемым шагом (сетка Go разъехалась с сеткой `runner.py`);
- `hops != len(path) - 1` — внутренняя инвариантная проверка маршрутизатора;
- в конце число снимков не равно `len(grid)`.

Это не паранойя: `TimeGrid()` в Go и `range(0, horizon, step)` в Python — две независимые реализации одной сетки, и молча разъехавшиеся метрики были бы хуже, чем явная 422.

## 14. Тесты

`make test` — всё зелёное, полный прогон ~13 с.

Три уровня:

**API-слой** (`internal/api/*/v1/*_test.go`). `httptest` + мок сервиса. Проверяют разбор URL/тела, коды статусов, форму JSON. `suite_test.go` собирает `chi.RouteContext` руками, чтобы `chi.URLParam(r, "id")` работал без роутера.

**Сервисный слой** (`internal/service/*/*_test.go`). Моки репозиториев и геометрии, `testify/suite`. Проверяют логику: маршрутизацию на синтетических графах, агрегацию метрик, ветки compare и what-if.

**Фикстурный слой** ([internal/service/run/fixture_test.go](../internal/service/run/fixture_test.go)). **Настоящий** Python на настоящих `data/*.json`. Это единственное место, где проверяется, что Go и эталон понимают друг друга одинаково. Сюит сам себя пропускает (`t.Skip`), если `python3` не найден или `geometry.py` не отвечает, — CI без NumPy не краснеет, но и не даёт ложной зелени: остальные уровни продолжают работать.

Моки в `*/mocks/` — **написаны руками** поверх `testify/mock`, конфига mockery в репозитории нет. Добавили метод в интерфейс — допишите его в мок, иначе пакет не соберётся.

Ожидаемые порядки на фикстурах (это же и есть проверка смысла, а не только кода):

| Фикстура | mean `path_ratio` | Что демонстрирует |
|---|---|---|
| `01_full_constellation` | ~0.98 | все пункты достигают цели |
| `02_first_launch` | ~0.19 | первая очередь: цель недостижима |
| `03_satellite_outages` | ~0.81 | отказы спутников роняют ниже цели |
| `04_link_range` | ~0.68 | видимость есть, ISL-сеть распалась |

## 15. Производительность

Замерено на фикстуре `01_full_constellation` (48 спутников, 3 плоскости, 3 клиента, 1 шлюз, 720 шагов), macOS/arm64, Go 1.25, NumPy 2.3:

| Операция | Время | Что происходит |
|---|---|---|
| `POST /api/projects` | ~0.2 с | валидация + один Python-процесс на smoke-снимок |
| `POST /api/projects/{id}/runs` | **~0.65 с** | один Python-процесс на весь горизонт + 720 × 3 BFS |
| `GET /api/runs/{id}/snapshot` | ~0.17 с | отдельный Python-процесс на один момент |
| `GET /api/runs/{id}/export` | ~0.001 с | из памяти, 167 КБ |
| `POST /api/runs/{id}/what-if` | ~1.0 с | валидация + smoke + полный прогон + compare |

Где узкие места, если понадобится ускорять:

- **Запуск процесса** — фиксированные ~0.15 с на импорт NumPy. Для `/snapshot` это почти всё время запроса. Лечится кэшем снимков по `(run_id, t_s)` или долгоживущим Python-воркером.
- **Маршрутизация** — `Route` вызывается `len(grid) × len(clients)` раз и каждый раз пересобирает граф с нуля. Шаги независимы, распараллеливаются тривиально; сейчас последовательно, потому что 0.65 с и так укладывается.
- **Память** — хранилище не чистится (см. §12).

Пятиминутный `middleware.Timeout` даёт запас примерно ×450 к текущему времени прогона.

## 16. Что учесть при доработке

**Не трогать `python/geometry.py`.** Это эталон организаторов. Всё, что нужно от геометрии, добавляется в `runner.py` или на стороне Go. Кстати, в `geometry.py` есть готовая функция `sunlight()` (освещённость / теневой участок) — сервис её пока не использует, но она доступна, если понадобится энергетический критерий.

**Детерминизм — часть контракта.** Сортировка списков смежности и порядок клиентов из JSON дают побайтово воспроизводимый ответ. Замена на обход `map` сломает это незаметно: тесты могут проходить, а UI начнёт «мигать» разными равноценными маршрутами между запросами.

**`t_s` в `/snapshot` не обязан лежать на сетке.** Валидация допускает любое значение в `[0, horizon_s]`, включая сам `horizon_s`, которого в сетке нет. Снимок посчитается (Python считает для произвольного `t`), но сохранённой записи маршрута для такого момента не будет, и `previousRoute` возьмёт ближайший шаг строго левее.

**Мёртвый код.** `islEdgeCount` и `satelliteIDs` в [visibility.go](../internal/service/run/visibility.go) используются только из тестов. Не принимайте их за живые хелперы.

### Рецепты

**Добавить эндпоинт.** Метод в интерфейс `service/service.go` → реализация отдельным файлом в `service/<домен>/` → метод в мок `service/mocks/` → хендлер отдельным файлом в `api/<домен>/v1/` → строчка в `initHTTPServer` → тесты на обоих уровнях → обновить [frontend.md](frontend.md).

**Добавить поле в сценарий.** Поле в `model.Scenario` → копирование в `CloneScenario` → правило в `ValidateScenario` (сверив с `geometry.validate()`) → при необходимости `configDiff` в compare → фикстуры.

**Заменить хранилище на БД.** Реализовать `repository.ProjectRepository` / `RunRepository` новым пакетом → переписать конвертеры под схему БД → поменять один геттер в `di.go`. Сервисы и API не трогаются.

**Подменить геометрию** (например, на нативную Go-реализацию для скорости). Реализовать `geometry.Client`, поменять `di.GeometryClient()`. Фикстурный сюит тут же покажет расхождение с эталоном — ради этого он и написан.
